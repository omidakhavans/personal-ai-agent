Phase 2 is complete as a local runtime. Phase 3 is a deliberate plan to make
that runtime durable and operable without turning it into a pile of unrelated
services.

## The starting point

The current system is intentionally compact:

```text
CLI -> Orchestrator -> JSON state -> stage executors -> Markdown artifacts
```

It already protects important behavior: evidence is bounded before a model sees
it, artifacts carry references forward, a review can block downstream work, and
a human must explicitly approve social transformation.

Files are not the problem. The limitation is that a file-backed local runtime
cannot conveniently provide cross-run history, an API, an operator control
plane, credential management, durable external publication records, or worker
coordination.

## The first move is a boundary, not a database

Phase 3.2 implemented framework-independent run, stage, artifact, and future
event records plus repository and artifact ports:

```text
workflow policy -> ports -> file adapter or PostgreSQL adapter
```

The current filesystem behavior remains the active first adapter. The existing
behavioral tests prove that the refactor preserved the content workflow before
PostgreSQL, FastAPI, or a UI are introduced.

Phase 3 raises the backend baseline to Python 3.12+ through an explicit,
tested compatibility change. FastAPI, Pydantic v2, SQLAlchemy 2, and Alembic
enter only when their API or database boundaries are ready.

That is a useful agent-engineering lesson: model calls, tool calls, and human
pauses are expensive or non-deterministic. Their safety rules should live in
application/domain policy, not be copied into every new transport or storage
layer.

## What has been implemented

Phase 3.3 adds the PostgreSQL-backed snapshot adapter and Alembic migrations.
Phase 3.4 adds append-only run events and storage-neutral query DTOs. Phase
3.5 exposes those read models through a versioned FastAPI adapter. The
filesystem adapter remains fully compatible, while the future control plane can
list and inspect PostgreSQL-backed runs without scanning directories.

## What comes next

1. A separate operator control plane for run history, artifacts, and explicit
   approvals. The learning site remains documentation only.
2. Versioned model, prompt, and tool configuration plus encrypted credentials.
3. A publisher port, starting with a human-controlled WordPress draft/preview.
4. Social publishing, background jobs, and observability after the audit,
   approval, and idempotency foundations are in place.

## Keep the categories separate

| Information | Intended responsibility |
| --- | --- |
| Run status, approvals, workflow history | relational operational data |
| Variable resume details | bounded, versioned checkpoint payloads |
| Research and content artifacts | controlled artifact storage |
| Model/publish credentials | encrypted credential records |
| Timings, trace IDs, diagnostics | logs, metrics, OpenTelemetry |

A business audit event answers "who approved this exact article?" Telemetry
answers "how long did the model call take?" Both are useful, but neither should
pretend to be the other.

## Explicit deferrals

The plan does not add a vector database, pgvector, LangChain, LangGraph,
microservices, or automatic publishing. There is no current retrieval use case
for vector search, and the existing evidence/approval workflow is more valuable
than infrastructure chosen by fashion.
